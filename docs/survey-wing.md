# Survey-wing integration: offline contracts

The OAK/PX4 multirotor remains the current capture platform. Issues
[#27](https://github.com/WalleringRobotics/mapping_functionality/issues/27) and
[#28](https://github.com/WalleringRobotics/mapping_functionality/issues/28) add a
second, explicit ArduPilot Plane/GigE platform. This first implementation checks
design inputs, plans and normalized event evidence offline. Live GigE acquisition,
raw UBX ingestion, measured calibration and Plane flight acceptance remain pending.

## Consume the design handoff

The supported producer is `uavdesign.integration`, schema
`wallering.uav-mapping-handoff/v1`, from
[the design repository](https://github.com/WalleringRobotics/UAV_Design_Environment/tree/c6b403c55170098037189024d5238f69bd62a685/integration).
The regression fixture was generated by that producer, using its actual source
inputs. `handoff-check` validates the version, identities and consumed fields,
then recomputes resource and camera geometry gates; it does not substitute for
the producer's complete JSON Schema validation.

```bash
wr-map handoff-check /data/design/mapping_handoff.json --output runs/wing-capabilities-001
```

The new output contains an exact handoff copy, `camera.json` for QGC's Custom
Camera, and `capability-check.json`. A missing storage measurement or a failed
budget returns exit status 2 and leaves the report. Existing output directories
are refused. Original input files are unchanged.

The camera definition derives the selected part, pixel dimensions, pixel pitch,
lens focal length and **requested** FPS. It is nominal planner geometry, not
measured intrinsics. The current design proposes 5320×3032 Bayer8 at 4 fps:
64,520,960 payload bytes/s, or 83,877,248 bytes/s with its 30% storage margin.
Its requested 50-minute recording window plus preroll/reserve needs
262,200,842,496 free bytes. The 50 minutes is a design request, not proven flight
endurance. Unpacked Bayer16 at 4 fps requires 1,032,335,360 payload bits/s and
fails even a 1 Gb/s link before overhead.

Camera limits remain SKU/mode dependent. Basler lists both default 5320×3032 and
full 5328×3040 dimensions, and different default/performance frame rates for
[a2A5320-7gcPRO](https://docs.baslerweb.com/a2a5320-7gcpro). The handoff's nominal
maximum does not establish the achieved rate. A future pylon adapter must read
back the actual mode, mosaic, ROI, firmware, chunk clock, native counters,
effective exposure/rate and packet diagnostics. `Bayer8_candidate` alone cannot
be imported as a calibrated RGB image.

## Check a Plane plan through the existing planner

Create a private copy of `configs/plane-limits.template.json`. Its null entries
intentionally fail. Supply the selected pack/payload, aircraft identity,
estimated or measured endurance with source hashes, reserve fraction, stall
margin, airspeed/bank/radius limits, wind bound and evidenced terrain assumption.
Bind the exact handoff and selected calibration profile SHA-256 values. A nominal
calibration profile may be fingerprinted for planning, but stays unqualified.

```bash
wr-map survey-check /data/plans/wing.plan \
  --handoff /data/design/mapping_handoff.json \
  --aircraft-limits /data/design/plane-limits.json \
  --output runs/wing-plan-001
```

Supported input is QGC Plan v1/Mission v2 with ArduPilot firmware type 3 and
fixed-wing vehicle type 1, containing continuous Survey items, explicit absolute
airspeed commands, takeoff and final landing. The existing PX4 command and
fixtures retain their defaults. Plane numbering includes home at index 0,
following [QGC's ArduPilot plugin](https://github.com/mavlink/qgroundcontrol/blob/v5.1.5/src/FirmwarePlugin/APM/APMFirmwarePlugin.h).
Downloaded mission contents still have to confirm this numbering.

The checker applies these conservative bounds:

- Minimum airspeed includes the stall margin and bank load factor. Maximum camera
  groundspeed uses airspeed plus the stated wind bound. Minimum progress uses
  airspeed minus wind. Conflicting camera/aircraft limits or zero headway fail.
- At the nominal 100 m, 25 mm lens, 2.74 µm pixels, 0.4 ms exposure and 0.6 px blur,
  the camera limit is 16.44 m/s. Terrain uncertainty reduces the useful height and
  tightens blur/overlap checks.
- Minimum turn radius is the larger of the declared radius and coordinated-turn
  radius. Adjacent segment lengths must fit the turns. Whole-turn envelopes,
  all path segments and direct return corridors must stay within the fence and
  avoid exclusions; thin exclusions between valid endpoints are detected.
- Time includes headwind transit, climb/descent, turn and launch/landing
  allowances plus an additional direct-return allowance. It must fit endurance
  after reserve for the selected pack/payload.

The supported terrain model is explicitly evidenced level ground at home.
Terrain-following, AMSL/terrain frame mixtures, RTL/loiter landing, rally points,
custom waypoint acceptance/pass radii and unsupported commands fail. Turn
envelopes are planning bounds, not a prediction of the tuned autopilot's path.
`flight_ready` and `survey_ready` stay false even when these checks pass.

The checked bundle preserves exact plan/handoff/aircraft hashes. Modifying a
camera, pack or profile requires a new check. The OAK capture command checks its
active profile hash and rejects Plane/GigE bundles until that recorder exists.
Offline `survey-legs` understands the Plane item numbering, rejects a late or
changed mission download, and compares speed/camera parameters as well as
navigation coordinates. Profile hashes propagate through leg reports, imported
image manifests, export metadata and processing reports/resume inputs.

Still required: actual QGC and Mission Planner saved Plane fixtures, Mission
Planner format support, Plane SITL mission/abort and recording endpoints, active
GigE hardware profile binding, and operator-reviewed real flight evidence.

## Normalized exposure-event boundary

`event-check` defines an offline boundary for future camera/F9P adapters. It does
not decode UBX, solve PPK or open any device. Preserve original RAWX, SFRBX,
TIM-TM2, trigger and ExposureActive records with source hashes beside any
normalized files. Counter unwrapping and counter alignment must come from
independent evidence; guessing these values cannot establish synchronization.

```bash
wr-map event-check /data/evidence/frames.jsonl /data/evidence/edges.jsonl \
  --timing /data/evidence/event-timing.json --output runs/event-check-001
```

Each frame row supplies `counter`, `counter_extended`, `epoch`, `timestamp_ticks`,
`clock_domain` and `exposure_ns`. Each edge supplies `counter`,
`counter_extended`, `epoch`, `polarity`, `time_system: "GPS"`, `week_is_full: true`,
`time_valid: true`, full `week`, `tow_ns` and `sigma_ns`. The timing profile follows
`configs/exposure-events.template.json`; only measured profiles with an alignment
evidence hash are accepted. Its signed delay maps the selected edge to exposure
start, and its separate duration uncertainty contributes half its sigma to the
midpoint uncertainty. Quadrature assumes independent uncertainties.

Matching uses the explicit counter offset and continuity epoch. Duplicate,
missing or reset counters/clocks disqualify the epoch; unmatched records are
retained. Opposite-polarity edges remain unmatched evidence. Explicit counter
wrap and GPS full-week rollover are supported; modulo weeks, UTC without an
explicit conversion, and invalid time are refused. Host receipt time never
becomes exposure time. Outputs copy exact input evidence and keep
`survey_ready=false`; physical event/optical timing and rigid-cage/antenna
calibration are separate acceptance gates.
